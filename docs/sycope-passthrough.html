Fronting the Recorder with Sycope Passthrough

How to route PCAP downloads and alert-triggered extractions through Sycope's Passthrough gateway instead of exposing the recorder directly — with role-based access, a central audit trail, and no shared secrets in the browser.

Applies to Sycope Recorder v2, Sycope 3.x Passthrough name recorder Recorder host [recorder.url]

What Passthrough is

Passthrough (Settings → Integrations → Passthrough) is a reverse-proxy gateway built into Sycope. A caller — a logged-in user or an alert action — requests a Sycope-hosted URL, and Sycope forwards it to a configured backend, injecting its own authentication into that outbound call. The caller only ever authenticates against Sycope; the backend's credentials never reach a browser or an alert engine.

This is distinct from External Destinations, which is Sycope calling out to a fixed URL as an alert action. The two compose: an External Destination can target a Passthrough URL instead of the backend directly, so alert-triggered calls get the same Sycope-mediated auth and audit trail as interactive ones.

Why the recorder uses it

The recorder's edge uses HTTP Basic Auth and a self-signed certificate. Routing through Passthrough instead of exposing that endpoint directly gives four things a direct link can't:

  • No shared secret in the browser — operators authenticate with their Sycope session; Sycope injects Basic Auth to the recorder server-side.
  • Role-based access instead of IP allowlisting — Access Rules gate by Sycope role per path and method, more meaningful than a broad RFC1918 CIDR list.
  • A record of who called it — every call is logged to Sycope's auditMessages stream (see below); the recorder itself keeps no log of who called it at all.
  • No certificate warning — the recorder's self-signed cert only has to be trusted by Sycope's backend, not by every operator's browser.

SSL Verify is a deliberate trade-off, not a default to ignore

The recorder's Caddy edge uses tls internal — a self-signed certificate. With SSL Verify off, Sycope skips validating it, which is acceptable on an internal network but weakens transport security. The durable fix is a certificate Sycope actually trusts — an internal CA imported under Settings → Security → Certificates, or a properly issued cert on the recorder — after which SSL Verify can be switched back on.

Access Rules

Two rules, because the recorder serves two kinds of traffic through the same backend: GET for PCAP downloads, POST for the alert webhook (/extract). A request matching no rule is denied by default — nothing extra is needed to block unlisted paths.

Path (regex)MethodRoles
^/downloads/.*GETAdministrators, service_zabbix, +2 custom roles
^/.*POSTAdministrators, service_zabbix, +2 custom roles

A trailing space breaks the regex silently

^/.* (note the trailing space) matches nothing — no request ever satisfies it, and Sycope returns a plain 401 with no indication the regex is the problem. Verify the exact stored string via GET /npm/api/v1/config/passthrough after saving, not just by re-opening the form.

Using it

Downloading a PCAP

Operators use a link of this shape — logged in, it downloads immediately, with no separate login prompt or certificate warning:

https://[sycope.url]/npm/api/v1/passthrough/recorder/downloads/<filename>

The recorder returns this URL directly in its webhook response (see Recorder-side change), so operators clicking a link in an alert never construct it by hand.

Triggering extraction from an alert

The alert's External Destination (REST client) action must point at Sycope, not the recorder:

unchanged — filter, before, after
Authentication
Basic Auth to Sycope (a service account with a role from the Access Rules table) — not to the recorder

There is no trusted-internal bypass

Calling /npm/api/v1/passthrough/… without Sycope authentication returns 401 — including calls from the alert engine itself. The External Destination action needs real Sycope credentials, exactly like an interactive user.

Recorder-side change

By default the recorder builds its download URL from SR_PUBLIC_HOST — the same variable Caddy uses for TLS SNI, so it can't simply be repointed at Sycope without breaking Caddy's own routing. An optional override replaces only the host part of the returned URL: 

# .env
SR_DOWNLOAD_URL_BASE=[sycope.url]/npm/api/v1/passthrough/recorder

With it set, extraction returns https://[sycope.url]/npm/api/v1/passthrough/recorder/downloads/<file> instead of the direct recorder URL. Unset, behavior is unchanged — existing deployments that don't use Passthrough are unaffected.

Verifying the setup

# 1. Log in, keep the session cookie
curl -sk -c cookies.txt -X POST https://[sycope.url]/npm/api/v1/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"<user>","password":"<pass>"}'

# 2. Confirm the stored config matches what the form shows
curl -sk -b cookies.txt https://[sycope.url]/npm/api/v1/config/passthrough | python3 -m json.tool

# 3. Simulate the alert webhook through Passthrough
curl -sk -b cookies.txt -X POST \
  'https://[sycope.url]/npm/api/v1/passthrough/recorder/extract?filter=full&before=30&after=30' \
  -H 'Content-Type: application/json' \
  -d '{"clientIp":"10.0.0.5","serverIp":"10.0.0.6","port":443,"protocol":"TCP"}'
# → expect a passthrough-prefixed download URL, HTTP 200

# 4. Download the file through the returned URL
curl -sk -b cookies.txt -o test.pcap 'https://[sycope.url]/npm/api/v1/passthrough/recorder/downloads/<filename>'
file test.pcap   # expect: pcap capture file...

A 401 at step 3 with no session cookie confirms Access Rules are being enforced — expected. A 502 usually means Sycope couldn't reach the recorder: check SSL Verify first, since a TLS handshake failure against a self-signed certificate also surfaces as 502, with no corresponding entry in the recorder's own Caddy logs to point at the real cause.

Audit Calls: what actually gets logged

With Audit Calls on, every Passthrough-mediated request writes an entry to auditMessages — Sycope's general audit log, the same stream that records logins and scheduled alert runs, not a Passthrough-specific one.

FieldMeaning
TimeWhen the call was made
UserThe Sycope user or service account that made the call
MessagePassthrough name, method, path, and status — e.g. Passthrough recorder GET /downloads/<file> -> 200
Method nameThe internal action type — record for Passthrough calls, updateUserPreferences etc. for others
SuccessWhether the call succeeded

The filename is in Message, not a separate column

auditMessages is not a Passthrough-specific log — it mixes in logins, logouts, and scheduled alert runs from every other part of Sycope. But for a Passthrough call, the free-text Message includes the full request line, so "who pulled which PCAP" is answerable here: filter by Method name = record (or search Message for Passthrough recorder) and read the path straight out of the message text.

Cross-checking against the alerts stream

For alert-triggered POSTs, the same download URL also lands on the triggering alert itself, in the REST API Response column of the alerts stream — the more direct place to find which PCAP one specific alert produced, without searching auditMessages text.

Two views of overlapping information

alerts → REST API Response — which file an alert produced, by alert.
auditMessages — every Passthrough call by every user or account, alert-triggered or interactive, with the filename embedded in free text rather than a dedicated column.

Practical filters

  • Filter auditMessages by Method name = record to isolate Passthrough calls from every other kind of audit entry (logins, preference changes, scheduled jobs).
  • Filter by User to see every account that has called the recorder through Passthrough — the recorder itself keeps no such log.
  • Filter by Success = false to surface failed Passthrough calls without shelling into the recorder's container logs.
  • To answer "which alert produced this file," start from the REST API Response in the alerts stream instead — it's a direct field, not free text to search.
